Estudo: Migração de Banco de Dados (SQLite -> PostgreSQL/MySQL)

Data: 13/01/2026 Contexto: Planejamento de evolução da infraestrutura do “Gestão de Editais”.

1. Respondendo às Suas Dúvidas

1.1 O PostgreSQL é gratuito?

SIM. O PostgreSQL é um software Open Source (licença PostgreSQL, similar à MIT/BSD), ou seja, é totalmente gratuito para uso pessoal, acadêmico e comercial. Você não paga licença, independente do tamanho do banco ou número de usuários. O mesmo vale para o MySQL (versão Community).

1.2 Posso trabalhar com ele localmente?

SIM. Você pode instalar o PostgreSQL no seu Windows de duas formas: 1. Instalador Direto (EnterpriseDB): Instala o servidor como um “Serviço do Windows”. Ele fica rodando em segundo plano na porta 5432. 2. Docker (Recomendado): Você roda o banco em um container isolado (docker run --name gestao-db -p 5432:5432 -e POSTGRES_PASSWORD=senha postgres). Isso evita “sujar” o seu Windows com instalações pesadas e é idêntico ao ambiente de produção.

1.3 Qual a vantagem de migrar (vs SQLite)?

O SQLite é um arquivo. O PostgreSQL é um servidor.

Característica SQLite (Atual) PostgreSQL/MySQL (Meta) Por que migrar?
Concorrência Bloqueia o arquivo inteiro na escrita. Se 2 usuários salvarem juntos, um dá erro. Suporta milhares de escritas simultâneas (MVCC). Essencial se o sistema for ter vários usuários logados.
Tipagem Fraca. Aceita texto em campo de número se forçar. Forte e Rigorosa. Garante a integridade dos dados. Evita erros “silenciosos” (ex: datas inválidas).
Recursos Básico (SQL padrão). Avançado (JSON, Arrays, Geoespacial). O Postgres tem suporte nativo a JSONB (ótimo para logs/históricos).
Backup Copiar arquivo .db. Dump SQL (pg_dump). Permite backups “quentes” (sem parar o sistema).

1.4 MySQL vs PostgreSQL?

Você mencionou conhecer MySQL. Ambos são excelentes, mas para Python/Flask, o PostgreSQL é geralmente o favorito por: 1. Melhor integração com o SQLAlchemy. 2. Suporte a tipos de dados avançados (Array, JSON). 3. Licenciamento mais permissivo (MySQL pertence à Oracle).

2. Como seria feita a migração?

Como você usa SQLAlchemy, seu código Python está 90% pronto. Você não escreveu SQL puro (SELECT * FROM...), você usou objetos (Bolsista.query...). O ORM cuida da tradução.

Passo 1: Preparar o Ambiente (Local)

  1. Instalar o PostgreSQL (ex: via Docker).
  2. Criar um banco vazio: CREATE DATABASE gestao_editais;
  3. Instalar o driver Python: pip install psycopg2-binary

Passo 2: Alterar a Conexão

No arquivo app.py (ou .env):

De (SQLite):

app.config['SQLALCHEMY_DATABASE_URI'] = 'sqlite:///gestao_editais_new.db'

Para (PostgreSQL):

# Formato: postgresql://usuario:senha@host:porta/nome_banco
app.config['SQLALCHEMY_DATABASE_URI'] = 'postgresql://postgres:senha123@localhost:5432/gestao_editais'

Passo 3: Criar as Tabelas

Ao rodar o sistema pela primeira vez conectado ao Postgres, o comando db.create_all() (que já está no seu código) vai criar todas as tabelas vazias automaticamente no novo banco.

Passo 4: Migrar os Dados (O Desafio)

Aqui está o trabalho real. As tabelas estão lá, mas vazias. Como mover os dados do sqlite para o postgres?

  1. Opção A (Script Python - ETL): Criar um script que conecta nos dois bancos ao mesmo tempo, lê do SQLite e grava no Postgres.

    • Vantagem: Controle total.
    • Desvantagem: Trabalhoso.

  2. Opção B (Exportação CSV): Exportar cada tabela do SQLite para CSV e importar no Postgres (COPY bolsistas FROM 'arquivo.csv').

  3. Opção C (Ferramentas Automáticas): Usar ferramentas como pgloader. Ele lê o arquivo .db e joga tudo para o Postgres magicamente. bash pgloader ./gestao_editais_new.db postgresql://user:pass@localhost/db

3. Resumo da Mudança (“O que muda?”)

  1. Código Python: Quase nada muda. Apenas a string de conexão.
  2. Infraestrutura: Você precisa ter o serviço do Postgres rodando (não é mais só um arquivo na pasta).
  3. Performance: O sistema ficará mais robusto para múltiplos acessos.

Minha recomendação: Mantenha o SQLite para desenvolvimento rápido agora. Quando o sistema for para produção real (com múltiplos usuários), fazemos a migração usando um script de ETL simples.
